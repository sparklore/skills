# 代码审核与审计

找出会影响正确性、数据完整性、安全或稳定性的缺陷。每条结论要有位置和依据，修复建议要能落地且不扩大改动面。问题数量不是目标。

仓库已有分级或审查规范时，以仓库规范为准。下面的 S/P 口径只在没有既定规范时使用。

## 边界

- 默认只输出结论和修复建议。用户明确要求修复时才改代码，且只改当前问题。
- 结论分成三档：已确认、很可能、待验证。没有代码、调用链、契约或运行证据时，不得写成已确认。
- 猜测标成待验证，并写清还缺什么。风格偏好标成非问题，不进问题表。
- 安全问题只写防御性修复。不写可直接用于攻击的操作步骤、payload 或利用链。
- 没有测量或明确性能目标时，不给数字结论。只指出代码上可见的 N+1、无界循环、全量加载、缺索引。
- 探索代码时沿用仓库已有检索约定，不另起一套。

## 先定范围

用户没点名时，审当前对话里的未提交改动。没有改动就审用户正在看的模块，并写明这个假设。

| 用户要的 | 范围 | 必答 |
|---|---|---|
| 审查这次变更 / diff / 提交 / PR | 该 diff 及其调用方、测试 | 是否实现预期、有无回归和无关改动 |
| 安全审计 | 点名的模块或仓库的信任边界 | 注入、越权、敏感数据、密钥、后端是否重复校验 |
| 正确性 / 可维护性 / 性能 | 点名范围 | 这三个维度里有证据的问题 |
| 上线前 / 能否合并或发布 | 待发布改动 | 有条件的合并或发布结论 |
| 只读审查 | 同上，按用户点名的范围 | 不创建、不修改、不提交任何文件 |

## 步骤

1. 写下审查对象、目标（合入把关 / 安全 / 上线前）、语言与运行时、相关契约和未知项。完成：范围能用一段话说清，未知项已列出。
2. 沿入口、调用链、数据模型和测试读代码。每条候选问题记下文件、符号和能支持判断的片段。完成：每条候选都有位置，或写明还缺哪段代码。
3. 只保留五个维度里实际成立的问题：正确性、安全、性能、可维护性、契约一致性。没有命中的维度不写「未发现问题」凑数。完成：问题表里没有风格项，也没有没有证据的项。
4. 每条标注维度、严重级别、优先级、确信度。严重级别看影响，优先级看是否挡住合并，两者可以不同。完成：级别和优先级都写了判断依据。
5. 给最小修复：复用现有写法，不改无关契约。破坏性建议（改接口、改数据模型、改状态机）写明影响面。完成：每条建议能单独验收。
6. 列出关键路径、边界、异常里没被现有测试覆盖的场景。完成：测试缺口表只含与本次风险相关的行。
7. 先给合并或发布结论，再给问题清单。完成：结论、Top 风险、剩余风险、未检查范围都在。

## 严重级别

- **S1 阻断**：数据丢失、可被利用的安全漏洞、核心功能不可用或大量用户受影响，且没有规避办法。
- **S2 严重**：关键功能异常，或较高的安全 / 数据风险，范围或后果低于 S1。
- **S3 一般**：非核心功能或边界错误，影响有限，或有替代路径。
- **S4 轻微**：可读性、命名、低影响体验。不影响正确性。

## 优先级

- **P0 立即**：不修则不合并、不发布。对应「必须修复」。
- **P1 高**：本迭代修，否则关键流程持续受影响。对应「建议改进」。
- **P2 普通**：近期迭代。对应「建议改进」。
- **P3 低**：可延后。对应「可选优化」。

信息不够时标暂定，并写需要确认的依据。不因问题多而降级，也不因单一技术偏好升级。

## 确信度

- **已确认**：能指出文件、行号或可复现行为。
- **很可能**：代码指向该问题，但触发条件或影响范围还缺一块证据。
- **待验证**：只有怀疑。写清要补的环境、数据或测试。

## 查什么

只报告命中的项。

- **正确性**：空值、缺字段、边界、精度、时区、并发与幂等、非法状态迁移、事务半截提交、重试与资源释放、被吞掉的错误。
- **安全**：注入、路径穿越、SSRF、反序列化；水平或垂直越权；弱会话与令牌；日志和响应里的敏感数据；硬编码密钥；只在前端做的校验；把第三方输入当可信。
- **性能**：循环内查询或外部调用、无上限分页、大对象重复加载、重复序列化。
- **可维护性**：职责混杂、重复实现、过深嵌套、魔法数字、错误信息无法定位或泄露内部细节。只在会妨碍修改或排障时报告。
- **契约**：路径、方法、参数、响应和错误语义的变化；可空性、默认值、枚举、精度；迁移与部署顺序；调用方未适配。
- **架构红线（见 `AGENTS.md` §5）**：是否出现「按业务用例硬编码」（如新增业务领域的 Go `capability`、专属 `/api/<domain>/*` 路由、或在 `widgetdsl` 中新增业务专属结构体 / `kind`，典型反模式见 `capability/ideas.go`、`server/ideas_gen.go`、`widgetdsl/ideas.go`），或把 SQLite 当现网活存储（违反 ADR-016 `docs/072`）；命中即判 **S1 / P0（不建议合并）**。

变更审查额外看：预期行为是否做完、是否误伤无关调用方、是否夹带无关格式化、测试是否断言可观察行为。

## 修复建议

- 只修当前问题。能扩既有函数就不新增分层。
- 不引入新依赖，除非现有手段做不到。
- 每条建议包含改哪里、改什么、怎样算修好。
- 用户没要求改代码时，建议停在文字和最小示例，不落盘。

## 输出

按这个结构写。没有问题的章节写「无」，不要删标题。简单到只有一两处时，保留第 1 节和第 3 节，其余可压缩。

```markdown
### 1. 审查结论

- **审查对象与范围：**
- **总体结论：** 建议合并 / 有条件合并 / 不建议合并
- **关键发现：**
- **剩余风险：**

### 2. 问题清单

| 编号 | 维度 | 严重级别 | 优先级 | 位置 | 问题描述 | 确信度 |
|---|---|---|---|---|---|---|

### 3. 问题详情与修复建议

按严重级别从高到低。每条包含：

- **位置：**
- **问题：**
- **依据：**
- **修复建议：**
- **验证方式：**

### 4. 测试缺口

| 场景 | 当前覆盖 | 风险 | 建议 |
|---|---|---|---|

### 5. 审查依据与限制

- 已检查：
- 未检查及原因：
- 需人工确认：
```

总体结论的口径：

- **建议合并**：没有 P0，剩余风险已写明。
- **有条件合并**：有 P0 以外的实质问题，或 P0 有明确、可在合并前完成的修复。
- **不建议合并**：存在未修的 S1/S2 且优先级为 P0，或关键路径未验证到无法判断。

## 澄清

只问会改变结论或修法的问题，最多 5 个。不重复用户已经给出的信息。同一种实现有两种解释、且结论不同时，把两种解释和对应结论写出来再问。
